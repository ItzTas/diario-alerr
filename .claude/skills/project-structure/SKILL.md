# Project structure: diario-alerr

The shape mirrors sei-monitor: a root `main.go` that only wires, shared code in `internal/core`,
one package per subject, HTTP features as layered modules, and Postgres through sqlc + goose.
Everything is in English: identifiers, packages, files, SQL, logs and user-facing text.

## Directory layout

```
.
├── main.go                    # main → run → assemble: config, database, watcher, HTTP modules, errgroup
├── database_test.go           # TestMain → coretest.Run for the root tests
├── integration_test.go        # the whole app through assemble, with fake gazette/ntfy/Telegram servers
├── .air.toml                  # go tool air: builds into ./tmp/main, reads .env
├── .env.example               # every environment variable, with the compose defaults
├── .githooks/                 # commit-msg (Conventional Commits) + pre-commit (gofmt, go test)
├── .github/workflows/         # docker.yml: vet + test against Postgres, then the GHCR image
├── .golangci.yml              # golangci-lint v2, standard set + gosec/errorlint/noctx/bodyclose
├── .prototools                # proto: pins the Go toolchain
├── Dockerfile                 # multi-stage; runtime is alpine + poppler-utils (pdftotext)
├── compose.yaml               # app only, read-only, no capabilities; joins the external `postgres` network
├── Makefile                   # check, lint, test, generate, dev, up, down
├── sqlc.yaml                  # schema=sql/schema queries=sql/queries out=internal/db (pgx/v5)
├── sql/
│   ├── schema/                # goose migrations + schema.go (embed + Migrate with a session lock)
│   └── queries/               # sqlc queries, one file per table group
└── internal/
    ├── core/                  # config.go, database.go, http.go, alert.go
    │   └── coretest/          # throwaway Postgres for tests (initdb or TEST_DATABASE_URL)
    ├── db/                    # GENERATED by sqlc, never edited by hand
    ├── gazette/               # WordPress media client, PDF text, term matching
    │   └── gazettetest/       # fake gazette site and PDF generator for tests
    ├── notify/                # Telegram and ntfy senders, Channels()
    ├── watch/                 # the monitor: service, cycle job, repository, alert text, state.json import
    └── modules/
        ├── feed/              # GET /feed.xml
        └── health/            # GET /healthz
```

## Root `main.go`

Only wiring. `main` builds the logger and the signal context and calls `run(ctx, logger)`;
`run` loads `core.Config` and calls `assemble(ctx, cfg, logger, now)`, which returns an
`*application` with `Run(ctx)` and `Close()`. Tests call `assemble` directly with a fixed clock,
so anything the app needs at boot goes through it. Nothing else lives at the root besides root
tests.

## Packages under `internal/`

- `core` is for what more than one package needs and that depends on no other internal package
  (`db` aside). One file per subject. `core` never imports a feature package.
- A subject package (`gazette`, `notify`, `watch`) owns its types and helpers. Helper code lives
  with the package that uses it; move it to `core` only when a second package needs it.
- Test helpers that other packages reuse get their own `<package>test` subpackage
  (`coretest`, `gazettetest`).

## HTTP modules (`internal/modules/<name>/`)

One file per layer, dependency direction `routes → handler → service → repository`:

- `types.go`: the module's `Options` and the request/response types.
- `repository.go`: a `Repository` interface and its `Postgres` implementation over
  `*db.Queries`. Domain errors (`ErrNotFound`, …) are declared here and matched upstream with
  `errors.Is`; `pgx.ErrNoRows` is translated here.
- `service.go`: the logic, depending only on `Repository`.
- `handler.go`: `net/http` handlers on a `Handler` struct; this is where errors become status
  codes and get logged.
- `routes.go`: `Configure(mux, pool, opts, log)` builds repository → service → handler and calls
  `RegisterRoutes(mux, h)`, which declares the patterns (`"GET /feed.xml"`).

To add a module, create the five files and call its `Configure` from `assemble`. Module tests use a
fake `Repository` and go through `RegisterRoutes` on a fresh `http.ServeMux`.

A periodic job lives in its own file named after the job, beside the service it drives
(`watch/cycle.go`), and is started from `application.Run`.

## Persistence

- `sql/schema/0000N_name.sql` are goose migrations (`-- +goose Up` / `-- +goose Down`). sqlc reads
  the same files as the schema. `schema.Migrate(ctx, url)` embeds them and runs them with the goose
  provider API and a Postgres session lock, so concurrent boots are safe; `core.OpenDatabase`
  calls it before opening the pool.
- **A schema change is always a new migration. Never edit one that exists.**
- **Migrations carry schema only.** Initial rows (the `monitor_state` singleton, the welcome
  alert) are written by the code (`watch.Service.Prepare`).
- `sql/queries/*.sql` hold the sqlc queries (`-- name: X :one|:many|:exec|:execrows`). After
  changing them or the schema, run `go tool sqlc generate` and commit `internal/db`.
- Times are `TIMESTAMPTZ`; `sqlc.yaml` maps them to `time.Time` (`*time.Time` when nullable).
  Integers are `BIGINT`.
- Multi-statement writes go through the repository's `inTx`, which runs the queries on
  `queries.WithTx(tx)`.

## Testing

- Write tests that describe what the code does now.
- Database tests: `database_test.go` with `TestMain` → `os.Exit(coretest.Run(m))`, then
  `coretest.Pool(t)` or `coretest.Database(t)` per test. Each gets a fresh database cloned from a
  migrated template.
- Anything that shells out to `pdftotext` skips locally when it is missing and fails under `CI`.
- `go test -race ./...` must pass; `golangci-lint run ./...` must report nothing.

## Tooling

- `air`, `sqlc` and `goose` are Go tool dependencies (`tool` block in `go.mod`); always run them
  with `go tool <name>`.
- Never change the versions pinned in `.prototools`.
